# Перенос Supabase: что и в каком порядке

Для того, кто отвечает за бэкенд (Айым). Документ описывает всё, что в QADAM Hub связано с Supabase, и что нужно сделать, если проект переезжает к другому владельцу, в новый проект или на другую платформу. Все названия файлов, таблиц и переменных взяты из репозитория на 31 октября 2026.

## 0. Сначала выберите вариант

| Вариант | Когда подходит | Объём работы |
|---|---|---|
| **A. Передать тот же проект другому владельцу** (Transfer project) | Меняется только аккаунт или организация, база остаётся | Минимальный: адрес, ключи, пользователи и данные не меняются |
| **B. Создать новый проект Supabase и перенести всё** | Нужен новый проект (другой регион, другой аккаунт, чистый старт) | Средний: около полдня, подробный чеклист в разделе 3 |
| **C. Уйти с Supabase на другую платформу** | Нужна другая база и другая авторизация | Большой: переписать авторизацию и права доступа, раздел 4 |

Рекомендация: если причина только в том, что проектом должен владеть другой человек, берите вариант A. Он не ломает ни сайт, ни пользователей.

## 1. Что сейчас завязано на Supabase

Текущий проект: `eiasrrisqpotiscifjpj`. Сайт, серверная функция и тесты используют только базу и авторизацию. Realtime, Storage, Edge Functions и cron не используются, к Supabase не обращаются боты на Oracle VM и GitHub Actions.

### 1.1 База данных (8 SQL-файлов в `supabase/migrations/`)

Запускаются вручную в SQL Editor, строго по порядку:

1. `202610180001_network.sql`: профили сети, связи, команды, приглашения, сообщения. Запускать один раз, повторный запуск на той же базе даст ошибку.
2. `202610200001_social.sql`: заявки в друзья, присутствие, добавление в команды. Один раз.
3. `202610230001_pilot_requests.sql`: заявки школ на пилот.
4. `202610240001_pilot_requests_validation.sql`: проверки полей для заявок.
5. `202610240002_cohorts.sql`: учебные заведения, потоки, ученики, прогресс, статусы, функции входа по коду.
6. `202610240003_opportunity_suggestions.sql`: предложения возможностей от студентов.
7. `202610310001_feedback.sql`: обратная связь.
8. `202610310002_feedback_rating.sql`: оценки звёздами. Требует, чтобы предыдущий файл уже был выполнен.

Таблицы в `public`: `network_profiles`, `network_connections`, `network_teams`, `network_members`, `network_invites`, `network_messages`, `network_friend_requests`, `institutions`, `institution_members`, `cohorts`, `cohort_learners`, `learner_progress`, `learner_activity`, `pilot_requests`, `opportunity_suggestions`, `feedback`. Закрытая схема `qadam_private` с функциями проверки прав. Расширение `pgcrypto` ставится первой миграцией. Доступ ограничен правилами RLS, они часть безопасности, не отключайте их.

### 1.2 Авторизация (настройки Supabase Auth, не лежат в репозитории)

Вход только по коду из письма: `signInWithOtp` с `shouldCreateUser: true` и `verifyOtp` (`src/components/NetworkAccess.tsx`). Это нужно воспроизвести в новом проекте руками:

- Включён провайдер Email.
- Шаблон письма Magic Link содержит `{{ .Token }}` (код). Проверьте и шаблон Confirm signup: для новой почты Supabase может отправить именно его, и там тоже должен быть `{{ .Token }}`, иначе придёт ссылка вместо кода. Проверяется отправкой кода на адрес, которого ещё нет в базе.
- Свой SMTP: сейчас Gmail (Authentication, SMTP Settings). Хост `smtp.gmail.com`, порт 465 или 587, логин ящик Gmail, пароль приложения Google (нужна двухэтапная проверка в аккаунте Google). У личного Gmail есть суточный лимит отправки, для роста нужен почтовый сервис.
- Rate Limits в Auth оставьте включёнными, срок и длину кода не меняйте, пока не проверите форму входа.
- URL Configuration: Site URL `https://www.qadamhub.com`, в Redirect URLs добавьте `https://www.qadamhub.com/**` и для разработки `http://localhost:5173/**`.
- Регистрация новых пользователей должна быть разрешена.

### 1.3 Переменные окружения (Vercel, проект `nvidia`)

| Переменная | Где | Что это |
|---|---|---|
| `VITE_SUPABASE_URL` | Production, Preview, Development | Адрес проекта, публичный, попадает в браузер при сборке |
| `VITE_SUPABASE_ANON_KEY` | Production, Preview, Development | Публичный ключ (publishable или anon) |
| `SUPABASE_SERVICE_ROLE_KEY` | только Production, Secret | Секретный ключ, нужен серверной функции `api/beta-feedback.js`. Никогда не с префиксом `VITE_` |
| `SUPABASE_URL` | необязательно | Если не задана, функция берёт `VITE_SUPABASE_URL` |

После любого изменения переменной нужен Redeploy: старый деплой её не увидит. Переменная `CRON_SECRET` в Vercel кодом не используется.

Ключи бывают двух форматов. Новый секретный ключ `sb_secret_...` не JWT и передаётся только в заголовке `apikey`, старый `service_role` (начинается с `eyJ`) работает в обоих заголовках. Наша функция умеет оба формата.

### 1.4 Код, который знает про проект

- `vercel.json`: политика безопасности CSP содержит адрес проекта дважды (`https://...supabase.co` и `wss://...supabase.co`). **Если не заменить адрес, сайт перестанет подключаться к базе.**
- `src/lib/network.ts`: создаёт клиент, хранит сессию в localStorage под ключом `qadam-network-auth`.
- `src/components/NetworkAccess.tsx`, `src/lib/cohorts.ts`, `src/lib/pilotRequests.ts`, `src/lib/opportunitySuggestions.ts`, `src/pages/NetworkPage.tsx`, `src/lib/networkInbox.ts`, `src/components/LearnerSync.tsx`, `src/components/FeedbackWidget.tsx`: обращения к таблицам, функциям и сессии. Менять не нужно, пока остаётся Supabase.
- `api/beta-feedback.js`: серверная запись обратной связи (ключ из `SUPABASE_SERVICE_ROLE_KEY`).
- Документы с упоминанием проекта: `CLAUDE.md` (раздел Project State), `NETWORK_SETUP.md`, `.env.example`, страница Privacy (Supabase указан как поставщик), `docs/IP_REGISTER.md` (условия и соглашение об обработке данных).
- Тесты `tests/network-db.test.mjs`, `tests/network-social.test.mjs`, `tests/feedback.test.mjs` запускают миграции во встроенном Postgres и от реального проекта не зависят. Тест `npm run test:network-ui` использует поддельный адрес.

### 1.5 Данные, которые копят пользователи

Аккаунты (`auth.users`), профили и сообщения сети, учебные заведения, потоки и ученики, заявки на пилот, предложения возможностей, отзывы. Сейчас проект предпродакшен, реальных пилотов и платящих клиентов нет, поэтому часто проще начать на чистой базе (раздел 3.8).

## 2. Вариант A: передать проект

1. Тот, кто передаёт, и тот, кто принимает, должны быть участниками обеих организаций Supabase (достаточно временно пригласить друг друга).
2. Откройте проект, Project Settings, General, раздел Transfer project, выберите новую организацию и подтвердите. Точное название пунктов и ограничения по тарифам проверьте в текущей документации Supabase, интерфейс меняется.
3. Адрес проекта, ключи, пользователи, таблицы и настройки Auth остаются прежними. Менять Vercel, `vercel.json` и код не нужно.
4. После передачи проверьте: SMTP и шаблоны писем на месте, вход по коду работает.
5. Затем смените ключи: Project Settings, API Keys, создайте новые и отзовите старые. Обновите `VITE_SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` в Vercel и сделайте Redeploy. Старые ключи были у прежних администраторов.
6. Обновите владельца в документах и в соглашении об обработке данных (раздел 6).

## 3. Вариант B: новый проект и перенос

### 3.1 Создать проект
Организация владельца, имя, пароль базы (сохраните в менеджере паролей, в чат не отправляйте), регион ближе к пользователям (Европа или ближайший). Регион влияет на то, где хранятся данные, проверьте это с текстом Privacy.

### 3.2 Применить схему
SQL Editor, для каждого файла из раздела 1.1 по порядку: New query, вставить файл целиком, Run. Читайте красные ошибки, не переходите дальше, пока они есть. В конце проверьте в Table Editor, что все 16 таблиц на месте. Если API не видит таблицу (ошибка `PGRST205`), выполните `notify pgrst, 'reload schema';`.

### 3.3 Настроить авторизацию
Всё из раздела 1.2. Проверка: войти по коду с новой почты.

### 3.4 Получить ключи
Project Settings, API: адрес проекта, publishable (anon) ключ и secret (service_role) ключ. Секретный ключ доступен администраторам проекта, храните его только в Vercel.

### 3.5 Обновить Vercel
Замените `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` во всех окружениях, `SUPABASE_SERVICE_ROLE_KEY` в Production, при наличии `SUPABASE_URL`. Redeploy.

### 3.6 Обновить код
Через PR в репозиторий:
- В `vercel.json` замените старый адрес проекта на новый в обоих местах CSP.
- В `CLAUDE.md` замените номер проекта.
- Если меняются условия, поправьте `docs/IP_REGISTER.md` и текст в Privacy.

### 3.7 Создать учебные заведения
Это делается вручную и нужно повторить в новом проекте. Сотрудник школы один раз входит на `/staff`, затем в SQL Editor:

```sql
select public.create_institution('Название', 'Город', 'почта-сотрудника@example.com');
-- второй сотрудник того же заведения:
select public.add_institution_staff('<id заведения>', 'почта@example.com');
```

Потоки и коды приглашения (`/student?code=...`) создаются в кабинете заново, старые коды в новом проекте не работают.

### 3.8 Данные: переносить или начать с чистого листа
- **Чистый старт** (рекомендуется, пока нет реальных клиентов): ничего не переносите. Пользователи войдут заново тем же кодом на почту.
- **Перенос**: нужен доступ к обеим базам. Данные выгружаются командой `pg_dump` (или `supabase db dump`) только по данным, отдельно для схемы `public` и для таблиц `auth.users` и `auth.identities`, затем загружаются в новую базу после применения схемы. Идентификаторы пользователей должны сохраниться, иначе ученики потеряют связь с потоками. Сначала отработайте это на пробном проекте, сравните число строк по каждой таблице и вход под реальным пользователем. Строки подключения содержат пароль базы, не вставляйте их в чат и в код.
- Приглашения в сеть хранятся хэшами, ссылки `/join#code=...` после переезда создайте заново в любом случае.

### 3.9 Проверка после переезда
Команды в репозитории: `npm run verify`, `npm run test:network`, `npm run test:feedback`, `npm run test:ui`.

Руками на живом сайте:
1. Вход по коду с новой почты (письмо пришло, код принят).
2. Страница Network: сохранить профиль, сделать вторую учётную запись и пройти проверку на двух устройствах из `NETWORK_SETUP.md` (раздел 3).
3. Форма заявки на пилот на `/welcome` и предложение возможности на Радаре: строка появилась в Table Editor.
4. Кнопка Feedback: отправить отзыв и оценку, строки в таблице `feedback`.
5. Вход сотрудника на `/staff`, создание потока, вход ученика по коду на `/student`.

### 3.10 Что почувствуют пользователи
Все сессии сброшены, нужно войти заново. В браузере сохранена прежняя сессия и кэш членства в потоке: приложение само их очистит и отправит ученика на `/student`. Локальные профили студентов на устройствах остаются, они не в Supabase. Ссылки на старые потоки и приглашения перестанут работать. Лучше делать переезд в тихое время и предупредить пилотные заведения.

### 3.11 Старый проект
Оставьте на 1-2 недели на случай отката (вернуть прежние значения в Vercel и Redeploy). Затем удалите: данные людей не должны оставаться в заброшенном проекте. Отзовите его ключи и удалите из Vercel неиспользуемые переменные.

## 4. Вариант C: другая платформа вместо Supabase

Если нужна не Supabase, придётся заменить три вещи:
1. **Авторизация по коду из письма.** Сейчас её даёт Supabase Auth. Нужен свой сервис писем и выдачи сессий.
2. **Права доступа.** Сейчас они живут в самой базе как политики RLS и функции в схеме `public` и `qadam_private`. Если база обычный Postgres без такого слоя, всю проверку прав надо перенести в серверный код.
3. **Клиентский код.** Шесть-семь файлов из раздела 1.4 напрямую вызывают клиент Supabase (`from`, `rpc`, `auth`). Их надо перевести на серверные эндпоинты.

Схему `supabase/migrations/` можно применить к обычному Postgres, но функции входа и RLS используют `auth.uid()` и роли `anon` и `authenticated`, которых вне Supabase нет. Грубая оценка: не меньше недели работы плюс повторные проверки безопасности.

## 5. Правила для секретов

- Секретный ключ только в Vercel (Production, Secret), никогда в репозитории, чате, скриншотах и переменных с префиксом `VITE_`.
- Если ключ хоть раз попал куда-то ещё, считайте его скомпрометированным: создайте новый и отзовите старый.
- Пароль базы и строки подключения хранятся в менеджере паролей.
- Публичный ключ и адрес проекта не секрет, защищает данные RLS. Не отключайте RLS ни на одной таблице.

## 6. Документы и юридические вещи при смене владельца

- Новый владелец принимает условия Supabase и соглашение об обработке данных (DPA) в своём аккаунте.
- Проверьте регион хранения и обновите `docs/IP_REGISTER.md` (таблица сторонних сервисов, строка Supabase).
- Страница Privacy называет Supabase поставщиком базы и входа. Если платформа меняется, обновите её в том же PR, где меняется код (правило проекта: список на странице должен совпадать с тем, что отправляет код).
- После переезда обновите `CLAUDE.md` и `NETWORK_SETUP.md`.

## 7. Краткий порядок для варианта B

1. Создать проект. 2. Выполнить 8 SQL-файлов по порядку. 3. Настроить Auth (шаблоны, SMTP, URL). 4. Скопировать URL и ключи. 5. Обновить переменные в Vercel и Redeploy. 6. PR с новым адресом в `vercel.json`. 7. Создать заведения. 8. Проверки из 3.9. 9. Через 1-2 недели удалить старый проект.
